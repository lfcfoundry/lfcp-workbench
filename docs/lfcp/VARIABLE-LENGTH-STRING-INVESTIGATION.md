# LFCP Variable-Length String Round-Trip Investigation

**Status:** writer-side defect reproduced in LFC-pack 0.4.19 / API 0. The exact low-level fault within the embedded WebAssembly string helper is not yet isolated. No fix is included here.

## Scope and evidence

The investigation used the canonical Workbench checkout on `main` at `48120ba885aadcc84d4d70ab02df89460f410137` and its pinned artifact `vendor/lfcp/0.4.19/lfc-pack.js`. The artifact provenance identifies JS-modules reference `6e16aa8044d0a05bafa7c756c949f3537c23e92a`, source blob `dae1cf4a7d9f6f568ea05447f57e9158e7396091`, LFC-pack 0.4.19 / API 0.

**Verified in source and execution:** Node.js `v26.13.0` on Android `arm64` reproduced the defect with generated bytes held in memory. No browser execution was needed for this library-level reproduction. The test is deterministic and compares every expected row and field; it does not use the Phase 3 sampler or `recordFor()` expected-value routine.

The original Phase 3 harness is `experiments/lfcp-first-spike/validation/phase3.js`; its preserved report is `benchmarks/results/phase-3-browser-20261102T132453Z-30069226.json`. That report records nine failed trials, with row 0 expected `body: ""` and actual eight-character values including `VTx8vKxt`, `pnjb4RUo`, and `bfXEI8qy`. The harness generated source and LFCP files in OPFS and removed them after each trial. The exact original source/output bytes are therefore not present for a byte-for-byte historical replay; the report, generator, expected samples, and actual samples remain available. The independent literal regression below recreates the failure without that expected-value generator.

## Minimal reproduction

The static logical rows are:

```jsonl
{"id":0,"body":""}
{"id":1,"body":"A"}
{"id":2,"body":"B"}
{"id":3,"body":"C"}
```

The LF-terminated input is 79 UTF-8 bytes. With default writer settings, `packRows()` produces one format 1.0 flat block (`kind: f`, 325 LFCP bytes). `info()` accepts the footer and reports 4 rows. `stats()` reports the `body` column as type `s`, `n: 4`.

| Row | Expected `body` | Actual `body` | Result |
|---:|---|---|---|
| 0 | empty string (0 chars) | `A` (1 char) | mismatch |
| 1 | `A` | `B` | mismatch |
| 2 | `B` | `C` | mismatch |
| 3 | `C` | property is `undefined` / omitted by `unpackText()` | mismatch |

There are four wrong body cells. `unpackColumns()` returns only three strings for the column although the block metadata says `n: 4`. The row APIs still return four rows. This separates semantic correctness from footer and row-count acceptance.

An independently specified six-row mixed-length fixture with body lengths `[0, 8, 40, 256, 1024, 4096]` also fails all six values. Its first actual value is the known `VTx8vKxt`; its last 4,096-character value is absent. This fixture uses fixed literal construction and does not call the Phase 3 expected-value code.

## Writer and reader paths

**Verified in source:** `packRows()` serializes rows and delegates to `pack()` (`vendor/lfcp/0.4.19/lfc-pack.js:1444-1445`). `pack()` and `packStream()` both reach `packMany()`; the stream writer packs completed chunks through `packMany()` (`:1442`, `:1458-1515`, `:1778-1810`). `packParallel()` assigns blocks to helper workers and stitches the result (`:1899-1950`).

**Measured:** for the 79-byte fixture, `packRows()`, `pack()` on the equivalent JSONL, and `packStream()` produced byte-identical 325-byte files. All three reproduced the same four value mismatches. A two-worker `packParallel()` run over two blocks also reproduced the failure in both blocks; its bytes matched `packStream()` in this run. These APIs exercise related `packMany()` writer logic and are not independent format implementations.

**Measured reader results:** `unpackRows()`, full `unpack()`, `unpackColumns()`, and `unpackText()` all expose the wrong values from the fast-writer file. They share the flat-column decoding implementation, so this is not evidence of four independent reader defects. `decodeColumn()` handles type `s` by UTF-8 decoding a frame and splitting on NUL (`:1033`). The returned values are short by one; row assembly does not reject that count mismatch. `unpack()` and `unpackRows()` are at `:1722` and `:1759`; `unpackColumns()` is at `:1745`.

## Root cause and binary-layout findings

**Established layer:** the defect is in the optimized flat writer path, not the fixture's expected-value logic and not an LFCP format limitation. `writeFlatBlockFast()` is selected for eligible blocks. Its entry guard returns `null` for exact mode, when WebAssembly is unavailable, or when input is under 64 bytes; later checks can also decline the fast path (`:1100-1101`). For eligible ASCII string columns it calls the embedded `strdict` helper and chooses among dictionary, joined-string, and other candidates (`:1130-1147`, `:1177-1185`). The flat block stores a string column using type `s`; the documented representation is the column's UTF-8 values separated by zero bytes (`:700-703`, `:917-918`).

The decisive control holds the logical rows, flat block kind, type `s`, reader, and API constant. With `global.WebAssembly` temporarily unavailable for that one Node call, the fast writer declines the block and the JavaScript `writeFlatBlock()` flat writer is used. It writes a 329-byte file, and the same `unpackRows()`, `unpack()`, and `unpackColumns()` reader paths return all four correct values. Explicit `{ block: 'nested' }` also round-trips correctly. This isolates the failure to the fast flat writer's encoding output; it does not prove which individual instruction in the embedded helper is faulty.

**Observed block evidence:** the accepted file has a valid footer, one flat block with four rows, a `body` string column declared with four values, and a decoded body vector of three strings. The public API does not expose decompressed frame byte offsets or a raw frame dump. The result is consistent with a string frame that omits one delimiter/value boundary; the precise compressed-frame bytes were not independently hex-dumped. No binary-format change is indicated by the evidence.

There is also a reader-side robustness gap: type-`s` decode does not verify that the split string count equals column metadata `n`. A reader guard could turn silent corruption into an explicit damaged-column error, but it cannot restore the lost source value and is not the primary correction.

## Trigger matrix and limits

**Verified by regression execution:**

- The source contains a 64-byte size guard. A 59-byte three-row fixture passes; the same logical three body values padded to 161 input bytes use the fast path and lose the first empty value. A two-row ASCII case over 64 bytes passed, so the evidence does not establish a simple input-size-only or row-count-only rule.
- With four rows and ASCII values, failures reproduced at body lengths 1, 7, 8, 9, 39, 40, 41, 255, 256, 257, 1,023, 1,024, 1,025, 4,095, 4,096, and 4,097 characters. Character length is not the observed boundary.
- Failures occur with one, two, and three flat columns; adding unrelated columns does not reliably avoid them.
- Empty-first unique values and an empty-first repeated value pattern both fail. Two-leading empties, an interior empty, an empty later in the column, and a different repeated pattern passed in tested cases. Therefore “first value empty” and column type `s` are not sufficient conditions by themselves.
- An eight-row low-cardinality column selected dictionary type `D` and passed. A mixed null column selected JSON type `j` and passed. A missing property in the first row, UTF-8 non-ASCII strings, and the tested UTF-8 character/byte distinction also passed.
- An eight-row cardinality sweep used the same empty-first arrangement and varied distinct string count from two through eight. Two distinct values selected `D` and passed; counts 3, 4, 6, 7, and 8 failed in the tested value arrangement; count 5 passed. This is non-monotonic evidence, not a cardinality threshold rule. A 12-row all-unique ASCII case also failed all 12 body values.
- A `packStream()` case produced two blocks, each with the failing empty-first pattern. Both blocks' values failed; footer row count was eight.

The exact threshold between the fast helper's string-dictionary/join branches and the specific values that produce a short vector remains unresolved. Some type-`s` controls pass, so type `s` alone is not a sufficient trigger. The Phase 3 high-cardinality variable-length workload is within the confirmed affected family.

## Regression coverage and result

Added `tests/lfcp-variable-length-string-roundtrip.cjs`. It checks every decoded cell from `unpackRows()`, `unpack()`, `unpackColumns()`, and `unpackText()` where applicable; records footer/count validation separately; tests `packRows()`, `pack()`, `packStream()`, `packParallel()`, a pure-JavaScript flat-writer control, nested encoding, size guard, length boundaries, cardinality, empty positions/frequency, null/missing values, UTF-8, column counts, and multiple blocks.

Run with:

```sh
node tests/lfcp-variable-length-string-roundtrip.cjs
```

The test intentionally exits nonzero while affected outputs mismatch. The recorded Node run is `benchmarks/results/phase-4-variable-string-roundtrip-20261102.json`: 49 case entries, 98 failing API comparisons (476 mismatches counted across repeated reader checks), and 37 passing control comparisons. These repeated checks expose the same logical defect through multiple APIs; they are not counts of unique root causes. Exit code 1 is the expected regression signal, not a claim that the current implementation passes. Re-run after a future vendor update; the expected acceptance condition is zero mismatches with all unaffected controls still passing.

## Findings and recommendations

1. **Corrective layer — writer:** investigate and correct the ASCII string path in `writeFlatBlockFast()` / embedded `strdict` handling. Preserve the current type-`s` semantics and LFCP format unless further evidence demonstrates a format defect.
2. **Defensive reader validation:** reject type-`s` columns whose decoded number of values differs from metadata `n`. Report this as a distinct library-reader hardening change; do not treat rejection as data recovery.
3. **Upstream/vendor:** a corrected LFC-pack release or source change is needed before updating the canonical vendor artifact. This phase does not modify the vendor copy or JS-modules.
4. **Compatibility:** the JavaScript flat writer demonstrates that the existing flat `s` representation can preserve these values and be decoded by the current reader. No format-version bump is evidenced. Files already written with lost values cannot be repaired from the LFCP output alone; retain original source data and require explicit re-import if affected output must be recreated. Reader hardening may change silent bad reads into errors for malformed files and needs compatibility tests.

## Remaining experiment at the Phase 4 handoff (resolved in Phase 5 below)

The narrow open question is which internal `strdict`/joined-string candidate branch emits the short type-`s` vector and why some adjacent cardinality patterns use the same public type but pass. The next useful upstream investigation is to instrument a diagnostic build of the fast writer around `strdict`, its output length/codes, and candidate selection, then compare those values with the JavaScript fallback for the literal matrix. Do not infer or change the binary format from the current evidence.

## Phase 5 follow-up: internal writer defect isolated

**Update, verified from the exact source revision and instrumented execution:** the Phase 5 diagnosis resolves the open question above. The embedded `strdict()` source at `JS-modules` commit `6e16aa8044d0a05bafa7c756c949f3537c23e92a`, `modules/lfc-pack/wasm/flatscan.c` lines 204 and 210, uses `if(o)` to decide whether to emit a NUL delimiter in both all-values join branches. An initial empty value leaves output offset `o` equal to zero, so the delimiter before the second logical value is skipped. Captured helper bytes for `['', 'A', 'B', 'C']` are `41 00 42 00 43`, while the JavaScript fallback emits `00 41 00 42 00 43`. The optimized output still declares four type-`s` values.

The exact reproduction, cardinality-branch explanation, diagnostic-copy provenance, and correction-layer recommendation are in [OPTIMIZED-STRING-WRITER-DIAGNOSTICS.md](OPTIMIZED-STRING-WRITER-DIAGNOSTICS.md). The canonical vendor file was not changed. The reader's missing decoded-value-count check remains a separate robustness requirement; it is not the cause of the writer defect.

## Phase 6 follow-up: isolated corrective candidate tested

The corrected source copy in `experiments/fixes/lfc-pack-0.4.19-string-writer/flatscan.c` changes both all-values joins to use `if(i)`. The loop ordinal expresses whether this is a later value; the output byte offset can remain zero after an empty string and cannot safely control separators. The candidate WebAssembly module was built with local Clang 21.1.8 and embedded in a separate copy of the wrapper. The canonical vendor artifact and the Phase 5 diagnostic snapshot remain unchanged.

The new 19-case targeted matrix passes against the corrected copy. It explicitly covers the early more-than-half-distinct and post-scan all-values branches, first/middle/final and consecutive empty values, all-empty and one-empty data, non-empty data, dictionary encoding, cardinalities 2–8, JavaScript fallback, and nested blocks. The original 49-case regression reports 98 failures against the pinned vendor and zero against the corrected copy. See `benchmarks/results/phase-6-string-writer-fix-final-v2-20261102.json` and the verification details in `OPTIMIZED-STRING-WRITER-DIAGNOSTICS.md`.

This is experimental validation on Node.js/Android arm64; the pinned vendor remains unchanged and still fails its regression. The fix is not yet an official LFC-pack release. Reader count validation remains separate and unimplemented; no LFCP format semantics changed.
